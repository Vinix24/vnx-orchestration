- Dispatch lifecycle (track `audit-spoor-kern`, K-3, ADR-045 §3/§4): the end finalizer is a new module, `scripts/lib/dispatch_lifecycle.py`. `finalize(project_id, dispatch_id, attempt, end_line, state_dir=...)` runs steps 1-5 of the plan — an exclusive intent (`state/dispatch_end/<project_id>/<dispatch_id>.<attempt>.json`, temp file plus `os.link`, exactly one winner across processes), the publication `flock` held through publication, the ledger line through the normal append layer from the intent's recorded byte offset, the projection of `dispatches.state` along the plan table "Eindtoestand naar projectie" (one `transition_dispatch` per step, actor `lifecycle`, `abandoned` = `timed_out` plus `metadata_json.end_state`), and `published_at` via temp file plus `rename`. `recover(...)` re-runs steps 2-5 under the same lock and re-applies the projection even when the ledger line already exists. The mode is read from the attempt's `dispatch_started` line, never from the live setting; a `legacy` dispatch is not finalized. The append rule is now the intent rule: a `dispatch_finished` is accepted only when the winner's intent exists for the key and its canonical form (sorted keys, no whitespace variance) is byte-equal to the line stored in it — a second end state with the same `outcome_id` (`timed_out` vs `abandoned`) is refused as `end_line_mismatch`, an end line without an intent as `missing_end_intent`. `transition_dispatch` and `transition_dispatch_idempotent` take an optional `project_id` that scopes the row read, the UPDATE, the returned row and the event (`WHERE dispatch_id = ? AND project_id = ?`); without it their behaviour is unchanged, so every existing caller keeps its semantics and remains to be converted. No schema change. `VNX_LEDGER_LIFECYCLE` stays off, and no lane calls the finalizer yet (K-5).
