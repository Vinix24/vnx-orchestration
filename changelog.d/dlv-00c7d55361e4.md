- CI (deterministische-testverificatie PR-3): a new `red-on-base` signal job turns the claim lines of the PR description (`**Red run** on <sha>:`, `Rode run:`, `Before the fix:` and the `RED_RUN_LABELS` the report contract defines) into `red_on_base.py --claims` input through `scripts/ci/red_run_claims.py`, then runs those tests on the merge-base and on the head. A `no_test` or unclaimed `green_on_base` verdict stays a neutral mark; only a `fails_on_head`, `incomplete` or false claim turns the job red. Not a required check yet.
  The job computes the merge-base of the base and head commits once and persists it as the `sha` output of the `merge_base` step; the test selection diffs against that value and `red_on_base.py --base` receives the same one. No step reads the base-branch tip after that computation, so a regression that landed on base after the fork cannot falsely confirm a claimed behaviour change.
- CI (deterministische-testverificatie PR-3): the `red-on-base` job lives in its own workflow, `.github/workflows/red-on-base.yml` (`name: Red on base`), triggered by `pull_request` with `types: [opened, synchronize, reopened, edited]`. `.github/workflows/vnx-ci.yml` is byte-identical to main again: no `edited` in its `on:` block and no `github.event.action != 'edited'` anywhere, so an edited PR body starts no `VNX CI` run at all. A skipped job still satisfies a required check, and a run in which every job is skipped concludes `success` — in the old shape an edit could supersede failed checks on the same head for both the required-check door and the merge rule that reads the latest `VNX CI` conclusion. The new job installs the test environment through `./.github/actions/profile-a-prelude` (the same pinned pytest and project deps Profile A uses) before `red_on_base.py` runs, which the earlier job did not.
