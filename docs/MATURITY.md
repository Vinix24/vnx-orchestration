# What works today vs what is opt-in

The tiers below were last checked against `origin/main` at `da297c55d` on 2026-11-12. I moved this page out of the README on 2026-11-22 at `95d533b42` and changed only its version facts then.

The audit trail is the whole point, so this section states maturity per feature. Verified against `origin/main` at `da297c55d` on 2026-11-12. `VERSION` is 1.10.0, released 2026-11-24; items marked "in 1.9.0" are in the 1.9.0 release and in every later one.

**Tier 1: in production.** Append-only NDJSON receipts, with hash-chain verification tooling (`audit_chain`) available but opt-in per project (`VNX_CHAIN_RECEIPTS`, off by default) and designed as epoch-rotation ([ADR-029](governance/decisions/ADR-029-hashchain-epoch-rotation.md)); the main ledger is unchained today. Multi-CLI provider hub, no vendor SDK. Review gates run a subscription reader first (codex) and DeepSeek on API credit second, with deterministic CI as the third gate. The single-entry dispatch door (`dispatch_cli.py`), default-on since 2026-06-24 ([ADR-024](governance/decisions/ADR-024-single-entry-door-default-dispatch-lane.md)), normalizing every lane and running a phantom-guard that rejects evidence-free GATE-GREEN receipts. Per-worker git worktree isolation, default-on since #1449, unconditional for the provider and subprocess lanes, with teardown classification for clean, committed, or dirty state. Headless `claude -p` is the only Claude lane since the interactive tmux dispatch lane was removed on 2026-09-18 (#1868); it bills the subscription, not API credits (see [BILLING.md](core/BILLING.md)). Zero-LLM context injection and repo map. Cost tracking per gate. Governed memory (past + current). The gate profile per project: review stack, round cap, takeover chain and plan-gate seats come from one fail-closed read ([ADR-060](governance/decisions/ADR-060-poortprofiel-per-project.md)), in 1.9.0. A review provider is one row in `GATE_LANE_ROWS` ([ADR-046](governance/decisions/ADR-046-een-poortmotor.md)), in 1.9.0.

**Tier 2: shipped, opt-in, burning in.** Smart routing (`VNX_AUTO_ROUTE`, honoured only on the raw-file legacy path and ignored by the single-entry door), elastic worker pool (`bin/vnx pool`), track layer + roadmap autopilot (`VNX_ROADMAP_AUTOPILOT=1`), auto-dream consolidation (`vnx dream install-scheduler` installs the nightly job and a 04:00 liveness watch, [ADR-066](governance/decisions/ADR-066-dream-liveness-watch.md); still burning in), and a self-learning loop that only proposes. The loop mines the receipt stream for recurring failures; with `VNX_LEARNING_LOOP_QUEUE=1` (or persist mode, `VNX_LEARNING_LOOP_PERSIST=1`) the proposals reach `pending_rules.json`, and an operator records the decision with `vnx learning decide-rule`. Nothing is applied without that approval, and the loop stops with a stated reason when its ledger verdict is refused. The injection A/B window is an operator step and no window has produced a verdict, so no effect on outcomes has been measured. Agents as folders (`VNX_AGENT_LAYOUT=shadow` or `on`, default `off`, [ADR-059](governance/decisions/ADR-059-agent-skill-native-materialisation.md)) and the signal-based second review seat (a per-project setting, active for this repository only) are in 1.9.0 and in the same state. These default off and are not yet proven at the Tier 1 bar. Roll back the dispatch door per terminal with `VNX_DISPATCH_LEGACY=1`.

**Tier 3: designed, not built.** Parallel multi-track execution, wave scheduler, merge lock, file-scope derivation. This is architecture, not a shipped feature ([ADR-020](governance/decisions/ADR-020-parallel-track-execution.md)): worktree isolation is not yet guaranteed race-free under parallel dispatch. Also designed, not built: operator steering beyond its first parts (source binding, class table, proposal store) has no analysis or proposals on main yet ([ADR-072](governance/decisions/ADR-072-operator-bijsturing-leert.md)), and a live T0 orchestrator on a non-Claude harness is not proven on this project.
