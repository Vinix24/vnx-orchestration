# Locks and releases: from dispatch to merge

> Register of every lock that work passes between a dispatch and a merge, and every way each lock opens.
> Read at base `cab945ad` (main after PR #2038), 2026-10-04. The code is authoritative: where a role, a
> doc or a comment says something else, this register states what the code does, and the difference is
> listed in the dispatch report that produced it.
>
> The register describes. It does not rate a lock and it does not propose a change.

## Terms

- **Lock**: a control in code that refuses, blocks or downgrades work until a condition holds.
- **Release**: anything that lets work pass a lock without the condition holding, or the intended human
  step the lock waits for. Five kinds: a command-line flag, an environment variable, an attest, a promote,
  a T0 decision.
- A flag or variable that only steers a helper script (a setup step, a benchmark, a report option) is not a
  release. It has a line in the [appendix](#appendix-names-that-are-not-a-release) with the reason.

## The six columns

| Column | Content |
|---|---|
| Lock | What the control holds back, in one sentence |
| Code | The file and the symbol (function, constant or subcommand). Never a line number: `scripts/ci/check_docs_file_line_refs.py` fails CI on a citation that drifts |
| Opens with | Each release with its exact spelling: the flag, the variable and its value, or the command |
| Who | Who the code lets use it, and where only a role or a doc says it belongs to someone. "Any caller" means the code checks no identity. "Env holder" means anyone who can set the environment of the process that runs the check |
| Trail | What the release leaves behind. "Nothing" means no record of the release was found |
| Test | The test that fails when the lock stops holding. "None found" means no such test was found |

An environment variable named `VNX_OVERRIDE_<NAME>` is also the generic form that `scripts/lib/config_registry.py`
`get` applies to any registry key: it beats the project config and the plain variable. The `VNX_OVERRIDE_<ID>`
form of a provider constraint is described in stage 1.

## Inventory this register covers

Measured at the base with the three commands below. Every name is either a release in a row or has a line in
the appendix. The `--force` flag is the one name with several uses: each use has its own row or line.

```
git grep -ohE 'VNX_OVERRIDE_[A-Z0-9_]+' -- scripts vnx_cli | sort | uniq -c
git grep -ohE 'VNX_[A-Z0-9_]*(OVERRIDE|BYPASS|SKIP|ALLOW|FORCE|DISABLE|LEGACY|UNSAFE|INSECURE)[A-Z0-9_]*' -- scripts vnx_cli hooks bin | grep -v '^VNX_OVERRIDE_' | sort | uniq -c
git grep -ohE "['\"]--(override|allow|force|skip|attest|no-verify|bypass|unsafe)[a-z0-9-]*['\"]" -- 'scripts/*.py' 'scripts/**/*.py' 'vnx_cli/**/*.py' bin | tr -d "'\"" | sort | uniq -c
```

| Inventory | Names |
|---|---|
| A: `VNX_OVERRIDE_*` variables | 12 |
| B: other variables that switch a control | 27 |
| C: command-line flags that open or skip something | 24 distinct, `--force` with 18 uses |

The patterns are a net. They miss releases whose name has none of those words, so the register also covers
releases found by reading the code (for example `VNX_REQUIRE_DISPATCH_TRACK`, `VNX_ADAPTER_T<n>`,
`VNX_REVIEW_GATE_TAKEOVER_CHAIN`, `--refire`, `--reopen-lane`, `--cutover-reason`) and the human steps of
`scripts/planning_cli.py`, `scripts/receipt_query.py`, `scripts/open_items_manager.py`,
`scripts/runtime_core_cli.py` and `vnx_cli/`. Further patterns used: `VNX_OVERRIDE_`, `override_applied`,
`allow-headless`, `allow-unstaged`, `approval_id`, `takeover`, `release_`, `PAUSED`, `SKIP_PERMISSIONS`,
`add_parser` over `scripts/planning_cli.py`.
